## 问题 1：前 10 秒声音很怪（歌曲与人声）　【已定位，是我的错】

### 现象
开头约 10 秒，人声和伴奏都很怪异，像在念什么东西。

### 根因
`lyrics_full_zh.txt` 第 2 行写了：

```
（前奏 8 秒，无词）
```

这是给我自己看的备注，但 **ACE-Step 把整段文件当歌词输入**，于是模型真的去唱「前奏八秒无词」这几个字，还带全角括号和阿拉伯数字。

### 修复
删掉这一行备注即可。ACE-Step 认 `[intro]` 这类段落标记，不认中文备注。

**教训**：给 TTS / 歌声模型的歌词文件里不能有任何“给自己看”的文字，只有段落标记和歌词本身。

## 问题 2：出现类似片假名的不明字体

### 现象
画面或音频里出现看起来像日文片假名的字符/发音。

### 可能根因（两条）
1. **音频侧**：ACE-Step 是多语言模型，歌词里的全角括号 `（）`、阿拉伯数字 `8`、以及中文备注，可能被 tokenizer 映射成日文假名发音。这与问题 1 同源。
2. **画面侧**：字幕文件 `subs_zh.srt` 用的是 `Microsoft YaHei`，正常不会出假名。如果确实在画面上看到，可能是 `drawtext` 渲染时字体回退到日文字体。

### 修复
- 先修问题 1，再看是否还有假名残留
- 若画面仍有，把 `drawtext` 的 `fontfile` 显式指定为 `msyhbd.ttc`（当前已经指定），并检查字幕文件编码

## 问题 3：人声和字幕对不上

### 现象
字幕出现的时间和实际唱到那一句的时间不一致。

### 根因
`subs_zh.srt` 的时间轴是**按「每句 6 秒」平均估算**的，不是真实演唱时间。

当时没有 ASR 工具，无法做强制对齐，只能猜。

### 修复
1. 安装 `faster-whisper`（本次安装未成功）
2. 用 ASR 把生成的歌转成带时间戳的文字
3. 用识别结果反推每句的真实起止时间，重新写 SRT

**注意**：ASR 识别的是“唱出来的音”，可能和原歌词有出入，需要人工核对。

## 问题 4：画面整体还是很糊

### 现象
1080p 输出，但近看仍然发虚。

### 根因
这一版用的是 **lanczos 插值放大**，不是 AI 超分：

```
1024×576（H3 原生） → lanczos 1.875x → 1920×1080
```

插值放大只是把像素拉大，不会重建细节。真正超分能更清晰，但代价极大：

| 方案 | 每段耗时 | 14 段总计 |
|---|---|---|
| lanczos（本版） | 26 秒 | 6 分钟 |
| RealESRGAN 4x 超分 | 22 分钟 | **5 小时** |

### 修复方向（按性价比排序）
1. **换 2x 超分模型**（`RealESRGAN_x2plus`）：输出只有 4x 的 1/4，速度约快 4 倍。本次下载的文件损坏（GitHub release 被截断），需重下。
2. **只超分关键段落**：开头 20 秒 + 每段副歌，其余保持 lanczos
3. **提高生成分辨率**：1024×576 是已验证稳定的上限；1280×720 会报 `shape invalid`（疑似 VAE 对特定 latent 尺寸有 bug）

## 附：本次还发现的两个技术限制

### A. H3 的 1280×720 不可用
实测 1024×576 与 1920×1088 都 success，唯独 1280×720 报：

```
shape '[1, 24, 1, 1, 22, 2, 40, 2]' is invalid for input of size 86400
```

原因未查明（不是 16 整除问题，1280 和 720 都能被 16 整除）。**结论：避开 1280×720。**

### B. 任务状态必须检查 `status` 字段
`/history/{pid}` 返回的条目即使 `status_str == "error"` 也算“存在”。只看 `pid in history` 会把失败当成功。本次因此白跑了 14 段。

正确判断：
```python
status = history[pid]["status"]["status_str"]  # 必须是 "success"
```
